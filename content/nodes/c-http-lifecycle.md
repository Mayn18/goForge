## Overview

Before you write a handler you should be able to say, step by step, what happens between a user pressing a button and your code running: name resolution, a TCP connection, possibly TLS, a request message, routing, a response, connection reuse. Most "mysterious" backend bugs (hung requests, double submits, caching surprises, CORS errors, 502s from a proxy) live in a step the developer never knew existed. This lesson builds that map and ties each step to the specification, so you can debug with evidence instead of folklore.

## Prerequisites

**Essential:** none. This is a concept lesson; you will use `curl` and a browser's developer tools. Having run any Go program is enough.

**Recommended:** *Goroutines & channels* (servers handle each connection concurrently); *Error handling*.

## How it works

### The journey of one request

```diagram
browser                  DNS            server / proxy                 your Go process
   │  1. resolve name ─────▶│
   │◀──── IP address ───────│
   │  2. TCP handshake (SYN, SYN-ACK, ACK) ───────▶ accept()
   │  3. TLS handshake (certificate, keys) ───────▶ (often terminated by a proxy)
   │  4. HTTP request  ───────────────────────────▶ parse → route → handler
   │◀─ 5. HTTP response (status, headers, body) ───  write
   │  6. connection kept alive for the next request, or closed
```

Each step has failure modes you can observe: a DNS failure is not a timeout; a refused connection is not a slow handler; a TLS error occurs before your code runs; a 502 is generated by a proxy, not your service.

### What an HTTP message is

HTTP/1.1 is a text protocol on top of a reliable byte stream (TCP). A request is a start line, headers, an empty line, and an optional body:

```
POST /api/chat HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 27

{"text":"hello","id":"42"}
```

A response is a status line, headers, an empty line, and an optional body. **HTTP is stateless**: each request stands alone; anything that looks like a session (cookies, tokens) is carried explicitly in headers.

HTTP/2 and HTTP/3 change the *framing* (binary frames, multiplexed streams on one connection) but keep the same **semantics**: methods, status codes, and headers mean the same thing. Go's `net/http` server speaks HTTP/2 automatically over TLS.

### Methods and their promises

| Method | Safe (no side effects intended) | Idempotent (repeating = same effect) | Typical use |
|---|---|---|---|
| GET | yes | yes | Read a resource |
| HEAD | yes | yes | Headers only |
| PUT | no | yes | Replace a resource |
| DELETE | no | yes | Remove a resource |
| POST | no | **no** | Create, or any non-idempotent action |
| PATCH | no | no (not by definition) | Partial update |

These promises are what let clients, caches and proxies behave correctly: a client library may retry an idempotent request after a dropped connection, and **must not** blindly retry a POST. "Idempotent" concerns the effect on server state, not whether the response is identical.

### Status codes: the contract with clients

Classes: 1xx informational, 2xx success, 3xx redirection, 4xx the **client** should change something, 5xx the **server** failed. Choosing correctly matters because clients, retry logic, caches and monitoring all key off them. Common intentional choices: 200 OK, 201 Created (with `Location`), 204 No Content, 400 Bad Request (malformed), 401 Unauthorized (really "unauthenticated"), 403 Forbidden, 404 Not Found, 405 Method Not Allowed (with `Allow`), 409 Conflict, 415 Unsupported Media Type, 422 Unprocessable Content (valid syntax, invalid semantics), 429 Too Many Requests (with `Retry-After`), 500, 502, 503, 504.

### Headers that change behavior

- `Content-Type` / `Accept`: what the body is and what the client can receive.
- `Content-Length` / `Transfer-Encoding: chunked`: how the receiver knows where the body ends. Getting this wrong corrupts the connection for the next request.
- `Cache-Control`, `ETag`, `If-None-Match`: caching and conditional requests (304 Not Modified).
- `Connection` and keep-alive: HTTP/1.1 connections are persistent by default.
- `Host`: lets one IP serve many sites.
- `Origin` and the `Access-Control-*` family: CORS, which is a **browser** policy, not a server security mechanism (see below).

### Same-origin policy and CORS

A browser forbids page JavaScript from *reading* responses from another origin (scheme + host + port) unless the server opts in with CORS headers. For "non-simple" requests (JSON content type, custom headers, methods beyond GET/POST) the browser first sends a **preflight** `OPTIONS` request. CORS protects *users*, not your server: `curl` ignores it, and a CORS error means the browser refused to *show* you a response that may well have been processed.

### Timeouts everywhere

A request has many clocks: DNS, connect, TLS handshake, time to first byte, total time, idle keep-alive. A server without timeouts can be held open forever by slow or malicious clients (the *Slowloris* family). Every network call needs a deadline.

> [!NOTE] This lesson is a concept lesson, so there is little Go code. Reading the specification text is the point: *RFC 9110* defines semantics, *RFC 9112* defines HTTP/1.1 messaging. They are long; use the table of contents, and read the sections named below.

## Practical examples

### Observe a request with curl

```bash
curl -v https://example.com/
curl -sS -o /dev/null -w '%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/
curl -i -X OPTIONS https://example.com/ -H 'Origin: https://other.example' -H 'Access-Control-Request-Method: POST'
```

On Windows PowerShell, `curl` is an alias for `Invoke-WebRequest`; call `curl.exe` explicitly (it ships with Windows 10 and later). Use double quotes in `cmd.exe`.

### A raw HTTP exchange with netcat

```bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
```

Port 80 shows the plaintext protocol. If `nc` is missing on Windows, use `curl -v http://example.com/` and read the `>` and `<` lines.

### A minimal Go server that exposes the lifecycle

```go
func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /echo", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "%s %s %s\nHost: %s\nUA: %s\nRemote: %s\n",
			r.Method, r.URL.RequestURI(), r.Proto, r.Host, r.UserAgent(), r.RemoteAddr)
	})
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

### Common mistakes

> [!PITFALL] **Using 200 for everything.** Errors returned as `200 {"error": ...}` defeat retry logic, caches, monitoring and generic client libraries.

> [!PITFALL] **401 versus 403.** 401 means "I do not know who you are" (and should carry a `WWW-Authenticate` header); 403 means "I know who you are, and you may not". Mixing them confuses clients that automatically refresh credentials.

> [!PITFALL] **Treating CORS as server security.** It is enforced by browsers for the benefit of users. Server-side authorization is still required; a permissive `Access-Control-Allow-Origin: *` with cookies is a vulnerability, and browsers refuse that exact combination.

> [!PITFALL] **Retrying non-idempotent requests.** A timeout does not mean the server did nothing. Retrying `POST /payments` without an idempotency key may charge twice.

> [!PITFALL] **Forgetting that GET can be cached and prefetched.** Never make a GET change state.

## Hands-on exercises

### 1. Read a conversation

Using `curl -v` against three different sites, annotate one full exchange by hand: each request line, each header and what it does, status line, and the response headers that influence caching and connection reuse. Identify whether the connection used HTTP/1.1 or HTTP/2 and how you know.

You are done when you can explain every header in your annotated transcript from the specification, and mark which are mandatory.

### 2. Time the steps

Use `curl -w` timing variables (or your browser's Network panel timing view) to break a request into DNS, connect, TLS, first byte and total for a site near you and one far away. Repeat each ten times and tabulate the medians.

You are done when you can explain which component dominates in each case, and predict what keep-alive and HTTP/2 change.

### 3. Specification lookup drill

For each of these, find the answer in RFC 9110 or 9112 and write the section number: (a) is DELETE idempotent, (b) what should a server send with a 405, (c) which status means "created" and what header should accompany it, (d) how a recipient determines the length of a message body, (e) what `Vary` is for.

You are done when you answered all five with section numbers and a one-sentence paraphrase, without a tutorial.

### 4. Break CORS on purpose

Run a tiny server on one port and a static page on another that calls it with `fetch` using `Content-Type: application/json`. Observe the browser's preflight in the Network panel, make the call succeed by adding exactly the headers needed and no more, then show that `curl` was never affected.

You are done when you can list the exact request and response headers of the preflight and explain what happens if the server answers the OPTIONS with a redirect.

## Engineering challenge

**Diagnose a misbehaving API from the outside.** Write a small Go server (about 100 lines) that deliberately contains six defects chosen from: wrong status codes, a missing `Content-Type`, a GET with a side effect, a response without a correct length, no timeout on slow clients, a broken 404 for unsupported methods, caching headers that make a changing resource stale, and a CORS configuration that blocks a legitimate call. Hand it to a friend (or your future self next week, after clearing your memory of the code) and have them find all defects using **only** `curl`, a browser, and the RFCs, writing a report that cites the specification section for each.

Constraints: the defects must be genuinely subtle (a status that is plausible but wrong), and at least two must only appear on the *second* request on a kept-alive connection or under a slow client. Edge cases to include in the report: HEAD behavior, `Content-Length` mismatch, and a request with a large body. The deliverable is the report; it should say how to fix each defect.

## Knowledge check

### 1. Retry or not

A client times out waiting for a response to `PUT /users/7` and to `POST /orders`. Which may be safely retried automatically, and why does the answer differ?

>>>
`PUT` is idempotent by definition: applying the same replacement twice leaves the same state, so a retry is safe in terms of server state. `POST` is not idempotent: if the first request succeeded but the response was lost, a retry may create a second order. Make POST safe to retry by giving the client an idempotency key that the server uses to deduplicate.

### 2. Where did that 502 come from

Your Go service logs nothing, yet clients see `502 Bad Gateway`. Which component probably generated it and how do you confirm?

>>>
A reverse proxy or load balancer in front of your service returned 502 because it could not get a valid response from its upstream (connection refused, reset, invalid response, or the upstream was down). Confirm by checking the response headers for the proxy's signature (`Server`, `Via`), the proxy's own logs, and by calling the service directly, bypassing the proxy.

### 3. Safe versus idempotent

Give a method that is idempotent but not safe, and a method that is neither. Why do caches and prefetchers care about *safe*?

>>>
`PUT` and `DELETE` are idempotent but not safe (they change state, but repeating them has the same effect). `POST` is neither. Caches, crawlers and browsers' prefetchers assume `GET`/`HEAD` are safe, so they may issue them without user intent; a GET with side effects will be triggered by link previews, crawlers and retries.

### 4. What CORS protects

An API returns `Access-Control-Allow-Origin: *`, yet you can still call it from `curl`, and a malicious server can too. So what does CORS actually restrict?

>>>
CORS restricts what **JavaScript in a user's browser** may read from another origin's responses (and which cross-origin requests the browser will send). It exists to protect users' ambient credentials (cookies, network position) from being used by hostile pages. It is not an access-control mechanism for the server: non-browser clients are unaffected, so authentication and authorization must be enforced on the server.

### 5. Why timeouts

A server accepts connections and reads requests with no read timeout. What attack or failure does this invite?

>>>
A slow-client attack (Slowloris): clients open many connections and send bytes very slowly, each holding a goroutine, memory and a file descriptor until the server runs out. The same happens accidentally with stalled mobile clients. Set read-header, read, write and idle timeouts and size limits on bodies.

### 6. 401 or 403

A request has a valid token but for a user who is not an administrator, calling an admin endpoint. Which status code and why?

>>>
403 Forbidden: the server understood the credentials and refuses to authorize the action. 401 is for missing or invalid authentication and should include `WWW-Authenticate` so the client can try again with proper credentials. Some systems deliberately return 404 for resources whose existence should not be revealed; that is a conscious information-hiding choice.

## Mastery criteria

- I can narrate the full journey of an HTTP request, including DNS, TCP, TLS, and keep-alive, and observe each step with tools.
- I can read a raw HTTP request and response and explain every header.
- I choose methods and status codes from the specification and can explain safe versus idempotent.
- I can explain CORS, including the preflight, and what it does not protect.
- I know which timeouts exist on a client and server and what each prevents.
- I look things up in RFC 9110/9112 and MDN instead of guessing.
